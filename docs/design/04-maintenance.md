# 04 保守と判断記録 — 変更時に迷わないために

## 変更したいときの案内

| 変更したいこと | 主に見る場所 | 影響と確認 |
|---|---|---|
| ボタン・色・余白 | shared/ui、テーマ、Penpot | 他画面、フォーカス、狭いPC幅 |
| 新しい装備・改修条件 | data/master、入力検証 | 参照ID、曜日、段階費用、既存計画 |
| 改修曜日の変更 | レシピと条件判定 | 既存の将来予定、未配置理由 |
| 取り込みJSONの変更 | infrastructure/import | 部分更新、未知ID、旧形式、秘密情報除外 |
| 不足数の計算 | domain/inventory・planning | 保護、自己割当、他目標、素材製造 |
| 翌日リスケ | domain/scheduling、application | 日本時間、休み、複数タブ、長期未起動 |
| 保存する項目の追加 | 保存スキーマ・移行・バックアップ | 旧データ復元、保存失敗、移行中断 |
| 艦娘・装備画像 | マスター画像対応・画像表示部品 | 改造差分、欠損、画像条件、容量 |
| 操作ガイド | 環境別の手順・画像 | 対象バージョン、個人情報、リンク切れ |

## マスター更新の流れ

```mermaid
flowchart LR
  A[出典を確認] --> B[差分を編集]
  B --> C[参照ID・費用・曜日・循環を検証]
  C --> D[架空の例題と実条件を照合]
  D --> E[PRで変更理由と影響をレビュー]
  E --> F[新しい版を配布]
  F --> G[利用者に変更点を表示]
  G --> H[将来予定を再計算]
```

実績は当時のレシピ版と実際の消費を保持します。新しいマスターで過去の費用を黙って書き換えません。将来予定は旧版との差分を確認できるようにします。取得失敗や検証失敗時は、未検証マスターへ自動置換しません。

## 判断記録の書き方

「何を選んだか」だけでなく、問題、理由、代案、影響、確認方法を1件ずつ短く残します。次の担当者が元の会話を読まなくても変更できます。

| 判断 | 状態 | 理由・次の確認 |
|---|---|---|
| 画面と計算を分離 | 設計提案 | 見た目の変更から費用・日程を守る |
| 共通マスターと個人データを分離 | 要求を反映 | 全装備対応と個人情報の非公開を両立 |
| 予定で実在庫を減算しない | 設計提案 | スキップ・取消で台帳が壊れるのを防ぐ |
| JSONを最新在庫として反映 | ユーザー確定 | 既存実績の再減算を防ぐ。06参照 |
| 同装備の複数目標は独立個数を合算 | 設計判断 | 09参照。同じ個体を二重達成にしない。黙って統合しない |
| ★以上／完全一致を選択可能 | 設計判断 | 09参照。既定は以上、厳しい条件から完成品を配分 |
| TypeScript等の技術候補 | 未採用 | technology-selection.md参照。版と互換性は製造時に確認 |

## 実装前に解決する事項

1. 74式EN 5.4.3の実画面撮影と実機取り込み検証。保存形式はソース確認済み。
2. 通常改修の失敗時に何が消費されるか、確実化の各段階、更新分岐の全件データ。
3. 最新JSON基準の保存境界、過去実績の履歴のみ訂正、複数タブ競合の実装検証。
4. 09/12と画面仕様で定めた複数目標・減数・削除・保護再照合を実装検証。
5. 09/12の同日再挑戦・素材前提順と探索366日の実装検証。
6. ゲーム画像の出典・公開利用条件と調達方法。実機スクリーンショットの取得。

これらは実装者の推測で埋めず、調査結果または利用者との合意を判断記録へ追加します。確定していない条件を実装の定数にしません。

## 意味のある検証例

| 確認 | 期待する結果 | 関連 |
|---|---|---|
| 装備のみを2回取り込む | 倍増せず艦娘・資材を保持 | A01/A02 |
| 完成1個と未完成2個、目標3個 | 残り2個だけを計算、完成品を保護 | A04 |
| 自工程への割当2個を持つ | 2個を二重に除外しない | A04 |
| 同日資材不足、翌日未完了 | 同日は仮配置、翌日に一度だけ再配置 | A06/A07 |
| JST境界を2タブで同時処理 | 繰越先が二重に作られない | A07/A10 |
| 再取込後に古い実績を訂正 | 照合の範囲を明示して二重減算しない | A09 |
| 保存中に失敗 | 完了を表示せず、旧状態を保持 | A10 |
| 画像がない、名称が長い | 名前と条件を確認して操作可能 | R22 |
| ガイドを見て両環境で操作 | 設定から反映後確認まで完遂 | R23/A11 |

公開前には受入基準を全件確認します。架空データのテスト成功は、全装備の実条件確認や74式ENの実機成功を意味しません。
